# Shared spend reservations (internal review)

Migration 030 moves admission, expiry, renewal, settlement and release to Postgres functions. Each function locks the same single mutex row and completes in one statement/transaction, so node-postgres Pool cannot split a transaction across connections. No lock is held during model I/O. The existing Meta/Claude/day/lifetime/rolling-user/feature policies and USD hold sizes remain; guard policies are rechecked inside admission after the lock. Per-user/per-pool concurrency remains eight, with a 20-second cancellable DB-polling wait instead of an instance-local queue. There is no FIFO guarantee across instances.

AsyncLocalStorage carries only a call's reservation ID and cancellation signal; it stores no budget or queue. onUsage atomically inserts one ledger row and retires that reservation. Duplicate identical settlement is a no-op; conflicting settlement fails. Cancellation/guard/provider failure releases the unused hold. Leases expire after ten minutes and renew every third of that interval; renewal failure aborts lease-bound Meta/Claude fetches. Crashes stop renewal, so holds do not remain indefinitely. Late provider usage is still recorded once, even after expiry, release or account deletion: hiding a real charge would falsify the ledger. Deleted-account IDs are removed from reservations.

Budget bounds still rely on the existing per-call reservation amounts being upper bounds on provider charges. Actual costs are always recorded, including unexpected excess or late charges; this work does not invent token-price guarantees. A partitioned/expired upstream request may still incur provider cost despite cancellation, which no database can undo. No paid call was used to measure that edge. Admission holds are conservative across UTC rollover, as before. Provider/tool ledgers remain separate; no new cash/credit allowance is introduced.

PGlite tests cover 40 parallel admissions via distinct client objects, daily/total/user/feature/provider limits, settlement races, duplicates/conflicts, expired/crashed holders, renewal, queue/abort/failure recovery, scaled personal shares and late usage after deletion. A real PostgreSQL multi-session/App Runner load test is not claimed. Migrations were applied only to disposable in-memory test databases. No deployment or production database access occurred.

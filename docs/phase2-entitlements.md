# Entitlements and store verification (internal, disabled development module)

EntitlementService defaults to disabled, ENTITLEMENTS_ENABLED parses to false, and neither the service nor any billing route/middleware is mounted in the production app. No app paywall or UI was added. Changing the env flag alone cannot turn billing or gating on. The existing account AI-consent middleware is untouched. All subscription strings in the StoreKit file are internal fixture data, not release copy. Prices remain provisional ($9.99/month, $79.99/year); nothing creates a real subscription or a charge.

Migration 032 stores one authoritative entitlement per account with none/trialing/active/grace/expired/revoked, platform/product/original transaction/expiry, immutable first-trial history and cancel-at-period-end. Store source records and processed-event IDs are separate from hunt usage. A short account-row lock serializes source updates, trial starts and quota admission inside SQL functions; no lock remains open over a store API call. Newer authenticated events supersede older ones; equal-time revocation/expiry outrank granting states. Cancellation retains access through the verified expiry; another current paid source can preserve cross-platform access. Account deletion cascades records.

Android/web trials use Postgres clock_timestamp(), fixed 14-day expiry, and no card or automatic purchase. Repeated starts, platform changes and reinstall/relink do not reset first-trial timestamps or the trial quota. iPhone trials require a verified, account-bound Apple introductory transaction, which is the provisional migration path for existing users. No existing production account was migrated. Actual Apple-ID eligibility is determined by Apple, not by this module or a browser-storage flag. Apple enrollment/commission is unknown (Ego required sign-in).

Fair use counts admitted hunts: ten across the entire trial and twenty per UTC calendar month for paid monthly/annual/grace access. Same request ID + server-computed request fingerprint returns duplicate (caller must replay or safely resume the existing job, never start a new hunt); a changed fingerprint is rejected. Failed work uses the same key for controlled job recovery, with no extra count. A fresh ID consumes another allowance. Job execution/recovery is not wired here; no automatic refund mechanism is claimed. None/expired/revoked block new premium work in this disabled module. Sign-in, saved reads, export, deletion, privacy and cancellation always bypass entitlement checks, even if the store/database is unavailable. Production hunt/update integration and read-only editing rules need separate review before any flag is wired.

Apple uses @apple/app-store-server-library 3.1.0 and pinned public [Apple G2/G3 root certificates](https://www.apple.com/certificateauthority/). The [maintained verifier](https://apple.github.io/app-store-server-library-node/classes/SignedDataVerifier.html) checks signatures, chain, Apple signing extensions, certificate validity at signedDate, bundle and environment. This wrapper additionally requires ES256/x5c, account binding, approved product IDs and bounded timestamps. Both the outer V2 notification and nested transaction/renewal JWS are verified. Online/OCSP checks are deliberately off: offline verification does NOT prove current certificate revocation status. Xcode/LocalTesting verification-bypass environments are rejected. Generated P-256 test roots/leaf/intermediate keys exist only during tests; no key or fixed test certificate is committed. Test roots are accepted only by explicit sandbox test construction, never production configuration.

Initial Apple transactions must match the authenticated account's appAccountToken before binding. Notifications update an existing binding; unlinked purchases cannot auto-grant an arbitrary account. Duplicate V2 notification UUIDs settle once. Refund/revoke, expiration, grace, renewal, cancellation and refund reversal are covered. Non-entitlement notification types fail closed; there is no public webhook endpoint or operational acknowledgement/retry worker yet. Real store reconciliation/receipt restore transport and account linking must be reviewed before public integration.

GooglePlayClient is a read-only interface to [purchases.subscriptionsv2.get](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.subscriptionsv2), supplied only as a mock here. Current API status, expiry and obfuscated account ID are authoritative, not the RTDN hint. A required GooglePushAuthenticator boundary must verify Pub/Sub OIDC issuer/audience/service-account identity before the processor runs; no permissive default or real credential client was implemented. Purchase tokens stay in memory for the API call; only SHA-256 token identifiers are persisted, with one account binding and linked-token checks. [RTDN](https://developer.android.com/google/play/billing/rtdn-reference) dedupe uses token hash + event time/type so repeated notifications dedupe without suppressing future renewals on the same token. Older event watermarks do not overwrite newer state. A real integration still needs authenticated transport, reconciliation and race/load validation against actual Play behavior.

apps/mobile/test-fixtures/Dandelist.storekit defines local monthly/annual products, one group and two-week introductory offers. Its JSON/product invariants are tested; opening/running it in Xcode and the signed-data behavior of real StoreKit/Play sandbox transactions are NOT verified on Windows. Local Xcode transactions do not establish an Apple production/sandbox certificate-chain test. No App Store Connect/Play products, keys, service accounts, agreements, permissions or store submissions were created. Those are explicit external gates, not an invitation for this branch to provision them.

Before any production use: Claude review, final product/price approval, authenticated sandbox end-to-end and restore tests, real server notification transports and reconciliation, consent/processor notices, and an explicit gated integration plan. Rollback must disable the new integration while retaining ledger/trial/purchase records; never drop paid entitlements to roll back code. No deployment, production migration, purchase, paid model request or spend occurred in Phase 2.
